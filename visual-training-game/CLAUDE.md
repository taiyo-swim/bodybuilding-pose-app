### A の補足（判断材料）

ピクセルの物理サイズは端末ごとに異なり、視距離も人ごとに違うため、
同じ設定でも網膜上の空間周波数は倍以上ばらつく。選択肢:

1. ppi補正のみ。視距離は40cm固定と仮定 — 実装は軽いが個人差が残る
2. フロントカメラで顔の大きさから視距離を推定 — 精度は上がるがカメラ権限が必要
3. 補正しない — ランキングの公平性が崩れる。採用しない

暫定方針: **v1は 1（ppi補正のみ）**。2 は Phase 3 以降の差別化機能として検討。
確定するまで、λ を扱うコードは「論理px」ではなく「視角（分）」を一次表現にしておき、
換算部分を差し替え可能な1箇所に閉じ込めること。

### B の補足

40試行で十分か、反転点の平均を取るか心理測定関数をフィットするかが未定。
実装前にシミュレーションで確かめる予定。決まるまで週次測定モードは着手しない。

## 1. プロダクト概要

一瞬だけ表示されるガボールパッチ（縞模様）の傾きを、リズムに乗せて判別し続けるゲーム。
知覚学習（visual perceptual learning）の研究で使われている刺激パラメータを、
そのままゲームのメカニクスとして採用する。

- ターゲット: スマホ利用時間の長い20〜30代
- 1セッション: 3分（1日1回で完結）
- 開発体制: 個人開発、3ヶ月でストア申請

### 何を作らないか

- 「同じ絵を探す」タイプのパズルは作らない（既存アプリと同じになり、訓練としても弱い）
- 長時間プレイを促す設計にしない（眼精疲労を招き、知覚学習の効率も上がらない）
- リアルタイム通信対戦は作らない（個人開発の規模で破綻する）

## 2. 技術スタック

| 領域 | 採用 | 理由 |
|---|---|---|
| クライアント | Flutter | UI実装が速い。ランキング・履歴画面のコストが低い |
| 刺激描画 | フラグメントシェーダー（GLSL） | ガボール生成はGPUで数行。CPU描画では間に合わない |
| 音声再生 | `just_audio` または `flutter_soundpool` | 低レイテンシ再生ができるものを検証して選ぶ |
| BGM | AI生成（決定済み） | 個人開発で曲数を確保するため。詳細は 2.1 を参照 |
| バックエンド | Firebase（匿名Auth / Firestore / Cloud Functions） | 認証不要で始められる。サーバー運用を持たない |
| ローカル保存 | `drift`（SQLite） | 試行ログを全件保持するため。KVSでは足りない |

Unityへの変更は、音声同期が実機で破綻した場合のみ検討する。その場合ランキング画面の実装コストが増える。

### 2.1 BGM の扱い

AI生成で用意する（決定済み）。実装側は以下を前提にすること。

- **BPMは120固定**、曲を差し替え可能な構造にする。曲ごとにBPMを変えない
  （譜面データの構造が単純になり、AI生成側の指定も安定する）
- 曲は**ループ可能な素材**として扱う。3分のセッションに合わせて尺を作らない
- 音源は `assets/audio/tracks/{track_id}/` に配置し、各ディレクトリに
  `meta.json`（生成サービス名・生成日・プロンプト・ライセンス区分）を必ず置く
- 生成サービスによっては商用利用の可否や権利帰属が契約プランで変わる。
  **どのプランで生成したかを `meta.json` に記録する。** ストア審査や後日の問い合わせで
  出所の説明を求められた際、これがないと詰む
- コンボでレイヤーが増減する演出のため、可能ならステム（ドラム・ベース・上物）を
  分けて書き出す。1枚のミックスしか得られない場合は、音量オートメーションで代替する

BGMが未完成の間は、クリック音のメトロノームで開発を進めてよい。
音声同期の検証（Phase 1 の項目6）はメトロノームで実施できる。

## 3. 中核仕様（ここが崩れると企画が成立しない）

### 3.1 刺激の生成

ガボールパッチ = 正弦波格子 × ガウス窓。

```
luminance(x, y) = 0.5 + 0.5 * C * exp(-(x² + y²) / (2σ²)) * sin(2π * xr / λ)
  xr = x·cos(θ) + y·sin(θ)
  σ  = λ （ガウス窓の標準偏差。波長と等しくする）
  描画サイズ = 6σ
```

- 背景は必ず中間グレー（sRGB 128）。周囲のUIも中間グレーに寄せる
- C（コントラスト）、λ（波長）、θ（向き）をシェーダーの uniform にする
- パッチの表示位置は**常に画面中央固定**。移動させない
  （中心視での課題として効果が報告されているため。動かすと探索ゲームになり質が落ちる）

### 3.2 ディザリング（必須）

8bit表示では中間グレー付近でコントラスト3%を表現しようとすると使える階調が±4しかなく、
縞が段々になって被験者は「縞」ではなく「量子化の輪郭」を見てしまう。

- シェーダーの最終出力に、1/255 スケールのノイズを加算して量子化誤差を分散させる
- 実装するまで、コントラスト5%未満の条件は信用しないこと
- 実機で低コントラスト条件を目視確認するまで、この項目は「完了」にしない

### 3.3 タイミング（フレーム単位で管理する）

**提示時間をミリ秒で指定してはいけない。** 内部表現は必ずフレーム数にする。

- 60Hz端末: 1フレーム = 16.7ms → 最短提示は2フレーム（約33ms）
- 120Hz端末: 同じ「2フレーム」でも16.7msになってしまう

→ 端末のリフレッシュレートを起動時に取得し、**目標msに最も近いフレーム数**に変換する。
   変換結果（実際の提示ms）は試行ログに記録する。推定値ではなく実測を残すこと。

想定する提示時間の段階: 150ms → 100 → 66 → 50 → 33ms

### 3.4 画面輝度の固定

プレイ中はアプリから画面輝度を固定し、終了時に元に戻す。
自動調光が効いていると実効コントラストが毎回変わり、測定値が無意味になる。

## 4. コアループ

1試行 = 1ノーツ。

```
固視点（ビートに同期して脈打つ） 約450ms
  ↓
ガボールを N フレーム提示
  ↓
（マスク条件のとき）ISI → 後続マスク
  ↓
回答受付: 縞の軸方向へのフリック
  ↓
正誤フィードバック → 次のビートへ
```

### 4.1 回答方式

**4択のフリック。** 縞の軸方向にフリックすれば正解。反対方向も正解扱い。

| 向き | 正解フリック方向 |
|---|---|
| 0°（縦縞） | 上 または 下 |
| 90°（横縞） | 左 または 右 |
| 45° | 右上 または 左下 |
| 135° | 左上 または 右下 |

- チャンスレベル25%。2択だと勘で50%当たってしまうため必ず4択にする
- 親指1本で操作できること。フリック距離の閾値は実機で調整（初期値: 24論理px）

### 4.2 リズムの扱い（重要）

**タイミング精度を採点対象にしてはいけない。**

一瞬見えたものを判断するには数百msの処理時間が必要で、
タイミングを厳しくすると「見えていないのに勘で押す」方が高得点になり、訓練として壊れる。

音楽は**メトロノーム兼ペースメーカー**として使う。

- 判定は正誤のみ
- 回答受付はビート丸ごと（BPM120なら500ms）
- 速く答えるとスコア倍率が上がる（精度ボーナスではなく速度ボーナス）
- コンボが繋がると音のレイヤーが増える、ミスで抜ける

### 4.3 適応的ステアケース

- 3連続正解 → コントラストを 0.85倍（難化）
- 1回ミス → コントラストを 1/0.85倍（易化）
- 正答率は約79%に収束する
- 上下限: 1% 〜 60%

この内部難易度は**プレイヤーに数値として見せない**。

## 5. 進行システム

### 5.1 二階建て構造

適応ステアケースは常に正答率79%を維持するため、上達しても体感難易度が変わらない。
そこで内部難易度と外部進行を完全に分離する。

| 層 | 性質 | 根拠 |
|---|---|---|
| 内部難易度 | 毎試行変動。非表示 | ステアケース |
| 経験値レベル | 単調増加。絶対に下がらない | 累計試行数 |
| ランク | 上下する | 週次測定の6軸合成スコア |
| リーグ | 毎週リセット | 同ランク帯30人での相対順位 |

**下がるものはランクだけ**にする。複数が下がると理不尽に感じる。

### 5.2 難易度の6軸

| 軸 | 操作するパラメータ | 難化方向 |
|---|---|---|
| コントラスト感度 | C | 小さく |
| 処理速度 | 提示フレーム数 | 少なく |
| 解像力 | λ（空間周波数） | 高周波へ |
| 側抑制耐性 | フランカー距離 | 4λ → 1.5λ |
| 時間分解能 | 後続マスクのISI | 150ms → 60ms |
| 持続力 | 試行数 / BPM | 多く・速く |

プロフィール画面でレーダーチャートとして表示する。6角形の形に個人差が出るので、
「自分は処理速度は速いが側抑制に弱い」といった個性が見え、共有動機になる。

### 5.3 解放スケジュール

軸は一度に全部開かない。**日数ではなく到達閾値を条件**にする。

| 順序 | 軸 | 解放条件の例 |
|---|---|---|
| 1 | コントラスト | 初回から |
| 2 | 処理速度 | コントラスト8%を安定通過 |
| 3 | 解像力 | 提示100msを安定通過 |
| 4 | 側抑制耐性 | 解像力ステージ到達 |
| 5 | 時間分解能 | 側抑制4λを通過 |
| 6 | 持続力 | 全軸解放後 |

### 5.4 頭打ちへの対処

知覚学習は6〜8週で飽和する。ここを設計に織り込まないと2ヶ月目で一斉離脱する。

救いは知覚学習の**特異性**（訓練した空間周波数・眼・視野位置に効果が限定されやすい性質）。
一般には弱点とされるが、コンテンツ設計上は「新しい条件 = 新しい学習曲線」を意味する。

シーズンコンテンツとして順に開放する:
- 新しい空間周波数帯（6.5 cpd で飽和 → 13 cpd で立ち上がり直す）
- 片眼モード（左右を別々に訓練）
- 周辺視モード（中心から外れた位置での検出）

**物理的限界を超えて難化させないこと。** リフレッシュレートの床や表示装置の階調限界に
達したら、その軸は「マスター済み」として封じ、別の軸に移す。

## 6. 対戦・ランキング（非同期のみ）

- **デイリーチャレンジ**: サーバーが日付からシードを配布。全員が同じ刺激列をプレイ
- **ゴースト**: 相手の試行ごとの正誤とタイムのみ保存（数KB）。画面端でコンボバーが競る
- **週次リーグ**: 同ランク帯30人。上位5人昇格・下位5人降格
- **属性別ランキング**: 年代別、1日のスクリーンタイム別

不正対策は、シードのサーバー発行と、反応時間分布の妥当性チェック（Cloud Functions）で足りる。

## 7. セッション設計

- **1日1回、3分で強制終了**。仕様として固める。「もっとやりたい」で終わらせる
- 週1回、**コンディション測定モード**を挟む
  - BGMもコンボもなし。純粋なステアケース40試行
  - ここで出た閾値を折れ線グラフに蓄積する
  - これが「効いている実感」を作る唯一の装置であり、将来のエビデンスの基礎にもなる
- ログインボーナス・連続記録の圧力は弱めにする（週5回でリーグ参加資格、程度）

## 10. 表現の制約（法務）

**アプリ名・説明文・スクリーンショット・アプリ内文言のいずれにも「視力回復」「視力が上がる」を入れない。**
非医療機器において「視力回復」は明確にNGとされる表現。

| 使ってよい | 使わない |
|---|---|
| 見る力を試すゲーム | 視力回復 |
| 目のコンディションを記録する | 視力が良くなる |
| スキマ時間のアイケア習慣 | 老眼が治る / 近視改善 |

- 研究の紹介は「こういう論文がある」という事実の提示に留め、自社アプリの効果として断定しない
- 体験談を載せる場合は「個人の感想です」を明記する
- ストアカテゴリは「ゲーム」

## 11. 実装フェーズ

### Phase 1（4週）— 刺激とコアループ

この段階で失敗したら企画自体が成立しないので、ランキングもリーグも作らない。

1. シェーダーでガボールを描画。コントラスト・λ・θを可変にする
2. ディザリングを実装し、実機でコントラスト2〜5%が滑らかに見えることを目視確認
3. リフレッシュレート取得とフレーム単位のタイミング制御。実提示msをログに記録
4. 4択フリック判定
5. ステアケース
6. BPM同期（音声とビートのずれを実機で計測）
7. 試行ログのSQLite保存

**Phase 1の完了条件**: 実機で60ms・3%コントラストの条件が正しく提示され、
試行ログの `ms_actual` が目標値の±1フレーム以内に収まっていること。

### Phase 2（4週）— デイリーと記録

8. Firebase匿名Auth
9. デイリーチャレンジのシード配布（Cloud Functions）
10. スコア送信とランキング表示
11. コンディション測定モードと閾値グラフ
12. レーダーチャート

### Phase 3（4週）— 進行と仕上げ

13. 経験値・ランク・リーグ
14. ゴースト対戦
15. 軸の解放スケジュール
16. 曲と背景の追加、ストア素材、審査申請

## 12. Claude Code への依頼のしかた

- **1タスク1コミット**。上の番号付き項目がそのままタスク単位になっている
- **シェーダーとタイミング処理は、モデルの目視確認ができない領域**。
  実装後に必ず実機で確認し、確認結果をコミットメッセージに書き残す
- 「動いたように見える」で進めない。低コントラストとタイミングは、
  数値ログ（`ms_actual`, `refresh_hz`）で検証する
- 仕様に迷ったらこのファイルを更新してから実装する。実装が先行して仕様が後追いにならないようにする
- **セクション0の未決事項に触れる作業は、推測で埋めずに止まって確認する。**
  「たぶんこうだろう」で進めた実装は、決定後にほぼ全て書き直しになる
- 決定した内容は、会話ではなくこのファイルに書く。セクション0から該当行を消し、
  本文の該当箇所を更新すること。セッションをまたいでも設計が揺れないようにする
